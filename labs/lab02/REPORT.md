### 2.2. Права доступа (задание 4.2)

```bash
$ touch example.txt && ls -l example.txt
-rw-r--r-- 1 rozhman rozhman 0 Nov 22 14:57 example.txt

$ chmod 640 example.txt && ls -l example.txt
-rw-r----- 1 rozhman rozhman 0 Nov 22 14:57 example.txt
```

Права `640` — это `6` (чтение и запись, 4+2) для владельца, `4` (только чтение) для
группы и `0` (ничего) для всех остальных. Владелец `rozhman` может файл читать и
править, участники группы `rozhman` — только читать, прочие пользователи не могут
даже прочитать файл.

Снятие всех прав и попытка записи:

```bash
$ chmod 000 example.txt
$ echo abc > example.txt
bash: example.txt: Permission denied

$ sudo echo abc > example.txt
bash: example.txt: Permission denied

$ cat example.txt
cat: example.txt: Permission denied
```

Обе строки выглядят одинаково, но причины разные, и обе объясняются одним правилом:
**перенаправление выполняет сама оболочка**, а не запускаемая программа. В первом
случае оболочка работает от имени `rozhman`, у которого нет прав на запись. Во втором
`sudo` повышает права только для команды `echo`, а файл `>` открывает всё та же
оболочка — по-прежнему от имени `rozhman`, поэтому отказ повторяется.

Обход без изменения прав: перенаправление нужно передать программе, запущенной от
root, — тогда файл открывает она сама.

```bash
$ echo abc | sudo tee example.txt
$ sudo cat example.txt
abc
```

`tee` получает данные по конвейеру и сам записывает их в файл, уже с правами root.

### 2.3. Переменные окружения (задание 4.3)

```bash
$ echo PATH
PATH

$ echo $PATH
/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin:/usr/games:...
```

`echo PATH` печатает слово `PATH`, потому что без `$` оболочка не подставляет значение
переменной. `echo $PATH` печатает содержимое: список каталогов через двоеточие.

```bash
$ which python3
/usr/bin/python3

$ python3 -m venv .venv
Error: Command '['/home/rozhman/projects/nids-service-BrilevRoman/.venv/bin/python3',
'-m', 'ensurepip', ...]' returned non-zero exit status 1
```

В минимальном образе нет пакета `python3-venv`, поэтому `ensurepip` недоступен и
создание окружения прерывается (подробнее — в разделе затруднений). После установки
пакета и активации окружения картина меняется: `which python3` возвращает
`~/projects/nids-service-BrilevRoman/.venv/bin/python3`, потому что активация ставит
каталог `.venv/bin` **в начало** `PATH`. Магии здесь нет: меняется только переменная
`PATH` (и `VIRTUAL_ENV`), а поиск исполняемого файла идёт слева направо, поэтому
найденный первым интерпретатор из окружения и запускается.

Разовая переменная окружения:

```bash
$ cut -d, -f15 data/connections.csv | sort | uniq -c
     76 dos
      1 label

```

`cut -d, -f15` берёт 15-ю колонку (`label`), `sort` группирует одинаковые метки

```bash
$ cut -d, -f7 data/connections.csv | tail -n +2 | grep -c "^udp$"
174

$ cut -d, -f13 data/connections.csv | tail -n +2 | sort | uniq -c | sort -rn | head -5
     92 ssh
     90 https
     88 http
     80 ftp
     76 smtp
```

Первый конвейер считает соединения по протоколу `udp` — 174 из 500. Второй строит
частотный список сервисов: `sort -rn` сортирует по убыванию счётчика, `head -5`
оставляет пять самых частых.

Разница между `>` и `>>`:

```bash
$ echo first > /tmp/a.txt; echo second > /tmp/a.txt; cat /tmp/a.txt
second

$ echo third >> /tmp/a.txt; cat /tmp/a.txt
second
third
```

`>` перезаписывает файл (первое значение потерялось), `>>` дописывает в конец.

Ошибка в файл, экран пуст:

```bash
$ ls /nonexistent 2> /tmp/err.log; echo "rc=$?"
rc=2
$ cat /tmp/err.log
ls: cannot access '/nonexistent': No such file or directory
```

`2>` направляет в файл только поток ошибок (дескриптор 2), поэтому на экране остался
лишь код возврата.

### 2.6. Виртуальная машина и снэпшоты (задание 4.6)

Гипервизор: Oracle VirtualBox, хост — Windows. Гостевая система: `ubuntu-server-lab02`,
Ubuntu 24.04.5 LTS (GNU/Linux 6.8.0-151-generic x86_64), пользователь `rozhman`.

1. При **выключенной** ВМ создан базовый снэпшот `clean` — состояние сразу после
   установки и первичной настройки. Зафиксировано дерево снэпшотов «до»
   (`snapshots-before.png`): единственный снэпшот `clean`.

2. ВМ запущена, у файла пакетного менеджера сняты все права:

   ```bash
   sudo chmod 000 /usr/bin/apt
   apt --version
   ```

   ```
   -bash: /usr/bin/apt: Permission denied
   ```

   Ломается не только сам `apt`, но и весь контур восстановления, который на него
   опирается: `sudo apt update`, `apt install --reinstall apt`, установка `tree` и
   прочих пакетов. Починка требовала бы ручного вмешательства (`sudo chmod 755
   /usr/bin/apt` либо переустановки пакета в обход `apt` через `dpkg -i` с заранее
   скачанным `.deb`) — то есть работы «вслепую» в уже повреждённой системе.

3. ВМ выключена, выполнен откат на снэпшот `clean` **без сохранения** текущего
   состояния (снимок повреждённого состояния не создавался). Зафиксировано дерево
   снэпшотов «после» (`snapshots-after.png`): в дереве отображается снэпшот `clean` и
   дочернее «Текущее состояние» без пометки `(изменено)`; ветка с повреждённым
   состоянием не создавалась.

4. ВМ запущена и выполнен контроль восстановления:

   ```bash
   stat -c '%A %U:%G %n' /usr/bin/apt
   apt --version
   sudo apt update
   ```

   Вывод в терминале ВМ после отката:

   ```
   rozhman@ubuntu-server-lab02:~$ stat -c '%A %U:%G %n' /usr/bin/apt
   -rwxr-xr-x root:root /usr/bin/apt
   rozhman@ubuntu-server-lab02:~$ apt --version
   apt 2.8.4 (amd64)
   rozhman@ubuntu-server-lab02:~$ sudo apt update
   Hit:1 http://archive.ubuntu.com/ubuntu noble InRelease
   ...
   Reading package lists... Done
   All packages are up to date.
   ```

   Установка `tree` и просмотр структуры проекта здесь не выполняются: в снэпшоте
   `clean` проекта ещё нет, каталог `~/projects/nids-service-BrilevRoman` отсутствует:

   ```
   rozhman@ubuntu-server-lab02:~$ tree -L 2 ~/projects/nids-service-BrilevRoman
   bash: tree: command not found
   rozhman@ubuntu-server-lab02:~$ ls ~/projects
   ls: cannot access '/home/rozhman/projects': No such file or directory
   ```

**Результаты.** После отката права `/usr/bin/apt` соответствуют штатным
(`-rwxr-xr-x`, владелец `root:root`), пакетный менеджер отвечает на `--version`
(версия `2.8.4`), `sudo apt update` отрабатывает без ошибок доступа. Ручные правки
прав не выполнялись — состояние восстановлено целиком механизмом снэпшотов.

**Вывод.** Снэпшот — это снимок состояния диска ВМ целиком, а не копия отдельных
файлов: откат возвращает всю файловую систему вместе с правами, владельцами и
содержимым каталогов. Поэтому он остаётся единственным практичным способом отмены
ошибок, которые затрагивают системные утилиты и тем самым лишают администратора
привычных инструментов восстановления. Практическое правило: снэпшот `clean`
создаётся до экспериментов, а откат выполняется **без** сохранения текущего
состояния — иначе повреждённая ветка остаётся в дереве и занимает место.
Обратная сторона той же особенности: откат стирает и безобидные результаты работы,
включая домашний каталог, поэтому `~/projects` после возврата на `clean` приходится
разворачивать заново (см. п. 4 в разделе затруднений).
Ограничения: снэпшоты не защищают от потери самого диска ВМ, не заменяют резервное
копирование и растут в размере по мере расхождения состояний.

**Ответ на п. 22 задания.** Размер снэпшота сопоставим с занятым местом на диске ВМ
(порядка нескольких гигабайт плюс приращение в разностном файле). Понять по нему,
что установлено в системе, нельзя: это двоичный слепок, а не список пакетов — для
инвентаризации служат `dpkg -l`, `apt list --installed`, `history` и файлы
конфигурации. Передать его коллеге тоже неудобно: гигабайты двоичных данных,
привязанных к гипервизору и версии ядра. Текстовое описание окружения
(`pyproject.toml`, `Dockerfile`, скрипт установки) и передаётся, и проверяется
несравнимо проще.

## 3. Ответы на контрольные вопросы

**1. Чем абсолютный путь отличается от относительного? Пример, где подмена одного
другим приведёт к ошибке.**

Абсолютный путь начинается с `/` и отсчитывается от корня файловой системы, поэтому
означает один и тот же файл из любого каталога. Относительный отсчитывается от
текущего каталога (`.` — он сам, `..` — родительский) и меняет смысл при смене
каталога. Пример: `python3 data/make_dataset.py` работает из корня проекта, но из
каталога `data/` тот же относительный путь превращается в `data/data/make_dataset.py`
и команда падает с `No such file or directory`; абсолютный путь
`~/projects/nids-service-BrilevRoman/data/make_dataset.py` сработал бы из любого
места. Обратная ситуация не менее опасна: `rm -rf ./build` в скрипте, запущенном не
из корня проекта, удалит чужой каталог.

**2. Что означают права 640 и кому что разрешено?**

Три разряда по три бита: владельцу `6` = чтение и запись (4+2), группе `4` = только
чтение, остальным `0` = никаких прав. То есть владелец читает и изменяет файл,
участники группы владельца только читают, прочие пользователи не имеют доступа даже
на чтение. Для секретов вроде `.env` это разумный минимум; для исполняемых файлов
такие права не годятся — нет бита выполнения.

**3. Почему `sudo echo abc > file` не обходит запрет на запись, хотя `sudo` есть?**

Перенаправление `>` выполняет оболочка **до** запуска команды и от своего имени.
`sudo` повышает права только для процесса `echo`, а файл открывает оболочка с
правами обычного пользователя, поэтому при отсутствии прав на запись возникает
`Permission denied`. Обойти запрет, не меняя прав, можно, передав запись программе,
запущенной от root: `echo abc | sudo tee file` — файл открывает сам `tee`.
Альтернатива — `sudo sh -c 'echo abc > file'`: перенаправление выполняет уже
привилегированная оболочка.

**4. Что содержится в `PATH` и на что влияет порядок каталогов в нём?**

`PATH` — список каталогов, разделённых двоеточием, в которых оболочка ищет
исполняемый файл, если имя команды указано без пути. Просмотр идёт **слева
направо**, и запускается первое найденное совпадение. Поэтому порядок определяет,
какая версия программы будет выполнена: каталог виртуального окружения в начале
`PATH` перекрывает системный `python3`, а случайно попавший в начало каталог с чужим
бинарником того же имени способен подменить любую команду — отсюда правило не
добавлять в `PATH` каталог `.` и посторонние папки.

**5. Как активация виртуального окружения Python меняет поведение команды `python`?
Через какой механизм?**

Активация — это выполнение скрипта `activate`, который меняет переменные окружения
текущей оболочки: ставит `.../.venv/bin` в начало `PATH` и выставляет `VIRTUAL_ENV`.
Никакой подмены системного интерпретатора не происходит: команда `python3`
по-прежнему ищется по `PATH`, но первой теперь находится `.venv/bin/python3`, а
вместе с ней — `pip` и консольные скрипты, чьи shebang-строки указывают на
интерпретатор окружения. Поэтому пакеты ставятся в `.venv/lib/.../site-packages`, а
не в системный каталог, и права root не нужны.

**6. Чем `>` отличается от `>>`, а `2>` — от `>`?**

`>` открывает файл на запись с обнулением содержимого — прежние данные теряются;
`>>` открывает на дозапись, и новые строки добавляются в конец. `>` перенаправляет
стандартный вывод (дескриптор 1), а `2>` — поток ошибок (дескриптор 2); `2>&1`
направляет оба потока в одно место, причём порядок важен: `> file 2>&1` пишет всё в
файл, а `2>&1 > file` отправит ошибки туда, куда указывал прежний stdout.

**7. Почему проект в `/mnt/c` работает медленнее, чем в `~/projects`?**

`~/projects` лежит на настоящей Linux-файловой системе (ext4 внутри виртуального
диска), а `/mnt/c` — это смонтированный диск Windows через промежуточный слой
(DrvFs/9p). Каждое обращение к файлу пересекает границу виртуальной машины и
преобразуется в вызов основной системы, поэтому накладные расходы возникают на
каждом `open`/`stat`: медленно работают `git status`, установка пакетов, запуск
тестов и любые операции с большим числом мелких файлов. Дополнительно теряется часть
семантики Unix — права и владельцы, чувствительность к регистру, символические
ссылки. Отсюда требование методички держать проект в домашнем каталоге.

**8. Что фиксирует снэпшот виртуальной машины и почему он не годится как способ
описать окружение для коллеги?**

Снэпшот сохраняет состояние ВМ целиком: содержимое диска, оперативную память и
регистры процессора, — и позволяет вернуться к этому состоянию за секунды. Как
описание окружения он непригоден: это двоичный слепок в несколько гигабайт, который
нельзя прочитать или сравнить построчно, нельзя частично передать и нельзя собрать
заново по текстовому описанию; по нему не видно, что именно установлено и в каком
порядке; он привязан к конкретному гипервизору и версии ядра, занимает место и
растёт с каждым расхождением. Окружение описывают текстом и кодом — `Dockerfile`,
`pyproject.toml`/`requirements.txt`, скрипты установки: их можно прочитать,
отревьюить, положить в Git и воспроизвести на любой машине.

## 4. Возникшие затруднения и способы их устранения

1. **`tree` отсутствует в минимальном образе Ubuntu Server.** Команда
   `tree -L 2` возвращала `bash: tree: command not found`, а `sudo apt install -y
   tree` — `E: Unable to locate package tree`. Решение: сначала обновить списки
   пакетов (`sudo apt update`), затем установить `tree`; для просмотра структуры без
   установки использовать `find . -maxdepth 2 -not -path './.git/*'`.

2. **Предупреждение о прокси `localhost` в WSL2.** При запуске команды выводилось
   `wsl: Обнаружена конфигурация прокси-сервера localhost… WSL в режиме NAT не
   поддерживает прокси-серверы localhost`. На работу `git` и `curl` внутри WSL это не
   влияло (GitHub отвечал `200`), поэтому предупреждение оставлено без правок; при
   необходимости прокси отключается в `/etc/wsl.conf` или переменными окружения.

3. **Права на `/usr/bin/apt` после эксперимента.** `sudo chmod 000 /usr/bin/apt`
   ломает не только пакетный менеджер, но и все способы его же починить. Решение:
   откат ВМ на снэпшот `clean` (раздел 2.6).

4. **Откат на `clean` возвращает всю файловую систему целиком, включая домашний
   каталог пользователя `rozhman`.** Поэтому после отката каталог `~/projects` (и
   `~/projects/nids-service-BrilevRoman` в частности) отсутствует — `ls ~/projects`
   отвечает `No such file or directory`. Это не ошибка, а ожидаемое поведение
   снэпшота, но проект приходится разворачивать заново:

   ```bash
   mkdir -p ~/projects && cd ~/projects
   git clone git@github.com:Ro4hman/nids-service-BrilevRoman.git
   cd nids-service-BrilevRoman
   python3 -m venv .venv && . .venv/bin/activate
   pip install -e ".[dev]"
   ```

   Правило на будущее: либо снимать снэпшот `clean` уже после клонирования проекта,
   либо держать рабочую копию в Git и разворачивать её скриптом.

5. **Нет `python3-venv` и `pip` в свежем образе.** `python3 -m venv .venv` падал с
   ошибкой `ensurepip` (`returned non-zero exit status 1`), а `python3 -m pip` и
   `python3 -m ensurepip` отвечали `No module named pip` и `No module named
   ensurepip` — в Ubuntu интерпретатор поставляется без них, отдельным пакетом.
   Решение: `sudo apt update && sudo apt install -y python3-venv python3-pip`, после
   чего окружение создаётся штатно. Дополнительно выяснилось, что имени `python` в
   образе не существует вовсе — во всех командах используется `python3`; в Windows
   это же место занимает `py`/`python.exe`, что и стало источником путаницы.

6. **SSH-ключ оказался недоступен внутри WSL.** `git clone` по SSH в свежей
   подсистеме зависал: в профиле WSL не было ни ключа, ни `known_hosts`. Решение:
   скопировать ключ из Windows в `~/.ssh` с правами `600` (каталог — `700`),
   добавить отпечаток через `ssh-keyscan -H github.com`, после чего
   `ssh -T git@github.com` ответил `Hi Ro4hman!`.

7. **Перенос готового кода из-под Windows в Linux.** Многострочные сценарии,
   передаваемые в `bash -lc`, обрывались по таймауту, а часть ошибок терялась в
   выводе. Решение: выносить длинные последовательности команд в отдельный
   `.sh`-файл и запускать его одной строкой `bash /mnt/c/.../setup.sh`, сохраняя
   вывод через `| tee /tmp/lab02.log`.
