### 2.2. Первый рабочий образ (задание 4.1)

`.dockerignore`:

свой размер в строке `transferring context`, но при отключённом `.dockerignore` он же

### 2.4. Кэш слоёв (задание 4.3)

Три замера (все — на одном и том же содержимом проекта):

| Сборка | Что изменилось | Время |
|---|---|---|
| №1 — первая, «наивный» порядок инструкций | — | 62 s |
| №2 — пересборка после правки `src/nids/api.py` | одна строка кода | 61 s |
| №3 — пересборка оптимизированного Dockerfile после той же правки | одна строка кода | 22 s |

После замера №2 порядок инструкций изменён: сначала копируется только
`pyproject.toml`, затем ставятся зависимости, и лишь потом копируется `src/`.
Слои установки зависимостей и обучения модели при правке кода остаются в кэше.

Использованное свойство кэша: слой переиспользуется, пока не изменились ни сама
инструкция, ни входные данные слоя. Так как `COPY pyproject.toml ./` идёт до
`COPY src ./src`, правка кода инвалидирует только нижние слои.

### 2.5. Многоступенчатая сборка (задание 4.4)

```dockerfile
FROM python:3.12-slim AS builder
WORKDIR /app
COPY pyproject.toml ./
RUN pip install --no-cache-dir --prefix=/install \
    "scikit-learn>=1.3" "fastapi>=0.110" "uvicorn[standard]>=0.27"
ENV PYTHONPATH=/app/src:/install/lib/python3.12/site-packages
COPY src ./src
COPY data ./data
RUN python data/make_dataset.py && python -m nids.train \
    && rm -f data/connections.csv

FROM python:3.12-slim
ENV PYTHONDONTWRITEBYTECODE=1 PYTHONUNBUFFERED=1
WORKDIR /app
COPY --from=builder /install /usr/local
COPY --from=builder /app/src ./src
COPY --from=builder /app/artifacts ./artifacts
RUN useradd --create-home --shell /usr/sbin/nologin appuser \
    && chown -R appuser:appuser /app
USER appuser
ENV PYTHONPATH=/app/src
EXPOSE 8000
CMD ["uvicorn", "nids.api:app", "--host", "0.0.0.0", "--port", "8000"]
```

Самый тяжёлый слой — `COPY /install /usr/local` объёмом **319 МБ**: это результат

пользователь и права — 365 кБ. В `v1` тот же `pip install` жил в слое на 330 МБ, но
рядом с ним оставались исходные данные обучения и кэш pip.

### 2.6. Безопасность и параметры (задание 4.5)

В «наивном» образе `v1` инструкции `USER` нет, поэтому процесс работает от суперпользователя:

```powershell
docker run --rm nids-service:v1 whoami
```

```
root
```

В многоступенчатом `Dockerfile` добавлен непривилегированный пользователь `appuser`:

```powershell
docker run --rm nids-service:v2 whoami
```

```
appuser
```

Сервис при этом отвечает: `{"status":"ok"}` на `/health`.

Путь к модели настраивается переменной `MODEL_DIR` (`src/nids/api.py` читает её,
по умолчанию — `artifacts`). Запуск с моделью, подключённой томом только для чтения:

```powershell
docker run --rm -p 8000:8000 `
  -v "${PWD}/artifacts:/models:ro" `
  -e MODEL_DIR=/models nids-service:v2
```

```
{"status":"ok"}
```

Ответ `/predict` с моделью из тома совпадает с ответом при модели, вшитой в образ.

## 3. Ответы на контрольные вопросы

**1. Чем образ отличается от контейнера? Что произойдёт с файлами, записанными внутрь
контейнера, после его удаления?**

Образ — неизменяемая последовательность слоёв, содержащая файловую систему приложения
вместе с интерпретатором и библиотеками. Контейнер — запущенный образ плюс тонкий слой
записи. Из одного образа можно запустить несколько контейнеров: слои образа у них общие,
а слой записи у каждого свой. Файлы, записанные внутрь контейнера, попадают именно в
этот слой записи и исчезают вместе с контейнером, если не подключён том или каталог
хоста. Кроме того, при старте контейнера слой записи пуст: изменения, сделанные в
предыдущем запуске того же образа, не наследуются.

**2. Почему контейнеры запускаются за доли секунды, а виртуальные машины — за десятки?**

Контейнер не запускает ядро и не проходит инициализацию оборудования: он использует
ядро хоста, а изоляция обеспечивается механизмами space и cgroups. Работы остаётся
немного — подготовить файловые системы (слои уже в кэше страниц) и стартовать один
процесс. Виртуальной машине нужен полный цикл: загрузчик, собственное ядро,
инициализация виртуальных устройств, `init` и службы, поэтому время измеряется
десятками секунд и больше.

**3. Что такое контекст сборки и зачем нужен `.dockerignore`?**

Контекст — это набор файлов, который клиент передаёт демону перед сборкой: содержимое
указанного каталога целиком, за вычетом перечисленного в `.dockerignore`. Он нужен,
чтобы уменьшить объём передаваемых данных и время сборки, не пускать в образ историю
Git, виртуальные окружения, датасеты и секреты. Важна и безопасность: всё, что попало
в контекст, может оказаться в слое, а слой потом не удаляется.

**4. Почему инструкции в Dockerfile располагают от редко меняющихся к часто меняющимся?**

Кэш работает по префиксу: если изменился слой, все последующие пересобираются заново.
Зависимости меняются редко, а исходный код — часто. Разместив установку зависимостей
до копирования кода, получаем: правка одной строки кода пересобирает только верхние
слои, а тяжёлая установка пакетов берётся из кэша.

**5. Секрет попал в слой образа и удалён следующей инструкцией. Останется ли он
доступным? Почему?**

Останется. Каждая инструкция порождает новый слой, а слои неизменяемы: `RUN rm` не
удаляет файл из предыдущего слоя, а лишь создаёт слой с «белой меткой» о его удалении.
Сам файл продолжает храниться в образе, и его можно извлечь, например, `docker save`
и распаковкой архива или просмотром слоёв. Поэтому секреты передают не через `COPY`,
а через BuildKit-секреты (`RUN --mount=type=secret`) или переменные окружения на этапе
запуска.

**6. Что даёт многоступенчатая сборка и за счёт чего уменьшается образ?**

Она позволяет оставить в финальном образе только результат, а не инструменты его
получения: компиляторы, заголовочные файлы, кэш pip, исходные данные, промежуточные
артефакты. В финальную ступень копируются лишь установленные пакеты и нужные файлы
(`COPY --from=builder`). Образ уменьшается за счёт того, что тяжёлые слои ступени
сборки в него не попадают. Дополнительно это уменьшает поверхность атаки: в рантайме
нет ни сборщика, ни лишних утилит.

**7. Почему сервис в контейнере должен слушать `0.0.0.0`, а не `127.0.0.1`?**

`127.0.0.1` внутри контейнера — это loopback самого контейнера, а не хоста.
Приложение, слушающее этот адрес, доступно только процессам внутри того же
контейнера, и проброс порта `-p 8000:8000` не поможет: соединение с хоста приходит
на сетевой интерфейс контейнера. `0.0.0.0` означает «все интерфейсы», поэтому
проброшенный порт работает. Это самая частая причина ситуации «контейнер запустился,
но сервис не отвечает».

**8. Почему `FROM python:latest` — плохая идея для продакшена?**

Тег `latest` не фиксирует версию: при каждой пересборке может подтянуться другой
образ, и сборка перестаёт быть воспроизводимой — «на моей машине работало» становится
нормой. Кроме того, `latest` обычно основан на полном Debian-образе с компиляторами
и лишними пакетами, то есть больше по размеру и шире по поверхности атаки. Для
продакшена фиксируют конкретную версию (а лучше — дайджест) и берут slim-вариант.

## 4. Возникшие затруднения и способы их устранения

1. **Docker отсутствовал на машине.** Команда `docker --version` не находилась в
   `PATH`. Решение: установка Docker Desktop через `winget`, затем запуск приложения
   и проверка `docker run --rm hello-world`. После установки бинарник лежит в
   `C:\Program Files\Docker\Docker\resources\bin`, и в новом терминале он уже доступен
   как `docker`.

2. **Git и рабочий каталог.** Репозиторий клонируется, но сборка запускается из
   корня проекта, поэтому первым делом выполняется переход в нужную папку
   (`cd C:\Users\Rozhman\Desktop\Konkin_labs\nids-service-BrilevRoman`) и создаётся
   ветка `feature/docker`. Запуск `docker build` из родительского каталога приводит к
   ошибке «Dockerfile not found» либо к сборке не того контекста.

3. **`-e .` в образе падал без исходников.** При установке проекта через
   `pip install -e .` в ступени сборки нужен хотя бы минимальный пакет, поэтому перед
   установкой создаётся заглушка `src/nids/__init__.py`, а настоящий код копируется
   следующим слоем. Иначе сборка прерывается на этапе разрешения зависимостей.

4. **Модель обучалась вне образа.** Первый вариант образа ожидал готовый
   `artifacts/model.pkl` с хоста, и на чистой машине сервис отвечал `503 model is not
   trained yet`. Решение: генерация датасета и обучение перенесены в `RUN` внутри
   образа, а `artifacts` и `data/*.csv` добавлены в `.dockerignore` — теперь контейнер
   самодостаточен.

5. **Сервис не отвечал после запуска.** Причина — `--host 127.0.0.1` в команде
   `uvicorn` (по умолчанию он слушает именно loopback). Решение: явный
   `--host 0.0.0.0`.

6. **Кэш не переиспользовался.** В «наивном» Dockerfile `COPY . .` стоял до установки
   зависимостей, поэтому правка одной строки в `src/nids/api.py` вызывала полную
   переустановку пакетов. Решение: сначала копируется только `pyproject.toml`,
   затем ставятся зависимости, и лишь потом копируется код.

7. **Пакеты из `pip install --prefix=/install` не попадают в `sys.path`.** При попытке
   обучить модель в ступени сборки сборка падала с
   `ModuleNotFoundError: No module named 'sklearn'`: установка с `--prefix` кладёт
   пакеты в `/install/lib/python3.12/site-packages`, а интерпретатор ищет их только в
   стандартных каталогах. Решение: добавить путь в `PYTHONPATH` —
   `ENV PYTHONPATH=/app/src:/install/lib/python3.12/site-packages`.

8. **Пакет-заглушка перекрывал реальный код.** Чтобы `pip install` мог разрешить
   зависимости без исходников, в ступени сборки создавался пустой
   `src/nids/__init__.py` и устанавливался как пакет `nids`. После копирования
   настоящего кода `python -m nids.train` падал с
   `No module named nids.train`: интерпретатор находил установленную заглушку, в
   которой нет подмодулей, и не видел реальные файлы. Решение: в ступени сборки
   ставятся только зависимости явным списком
   (`pip install --prefix=/install "scikit-learn>=1.3" "fastapi>=0.110"
   "uvicorn[standard]>=0.27"`), а код подключается через `PYTHONPATH=/app/src`.
   Это же убрало лишнюю зависимость сборки от заглушки.
